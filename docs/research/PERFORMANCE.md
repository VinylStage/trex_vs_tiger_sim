# Performance research and profiling: T-Rex vs Tiger simulator

Track: **perf** · Date: 2026-10-19 · Measurements in a scratch copy; the repository was not modified

## TL;DR

- **The engine is the main cost at scale.** Throughput falls from 3.5 M agent-steps/s at 10v100 to 0.58 M at 500v5000, so the per-agent cost grows with population. At 500v5000, `SpatialGrid.nearest` plus its filters take about 65% of CPU. 96% of those calls come from **routed tigers** that look up the nearest T-Rex on every tick.
  - An **exact** fix (search only the bounding box of occupied cells) gives 1.07–1.45x with bit-identical results.
  - A **model-changing** fix (routed tigers re-pick their flee target on the existing 1 s retarget timer) gives 1.3x at 10v100, 2.1x at 50v1000 and 4.0x at 500v5000.
- **Main-thread jank comes from three places:**
  1. Aggregation runs on the main thread. 20,000 runs cause a **602 ms** long task; 5,000 runs cause 222 ms. About 85–90% of that is the Spearman sensitivity loop, which re-ranks the same vector 22 times. Ranking once and using typed arrays makes that part 2.0–2.6x faster with identical results; moving it to a worker removes it from the main thread entirely.
  2. The **language toggle rebuilds the whole form and redraws the charts twice.** That is a 96 ms interaction unthrottled and **560 ms at 4x CPU**, which is "poor" INP (>500 ms) per [web.dev](https://web.dev/articles/inp).
  3. **Startup builds the whole UI in JS**: one 450–690 ms long task at 4x CPU. Lighthouse mobile (simulated) reports TBT 220–380 ms and max-potential-FID 430 ms.
- **Production (remote `main` 21c02f5) adds self-hosted Pretendard:** about 390 KB of fonts on first view (14 subset files). That adds 6–8 extra 58–175 ms long tasks in the first ~3 s (4x CPU, slow 4G) as each subset swaps in. Lighthouse with applied throttling goes from FCP/LCP 1.84–1.94 s / TBT 0 ms to 2.22–2.53 s / 400–490 ms.
- **Replay** holds 60 fps up to about 1,000 agents. At 5,500 agents it drops to 20–28 fps, and the bottleneck is rasterising 5,000 arcs, not JS (JS draw is only 4–6 ms per frame). A one-line level-of-detail change (squares when the radius is under 3 px) gives **25–28 → 43–51 fps** in the same environment.
- **Bundles are already small:** 21.5 KB brotli JS, 5.7 KB worker, 3.0 KB CSS before fonts. The font is now 90%+ of the bytes.
- **Do not adopt SharedArrayBuffer.** It needs cross-origin isolation (COOP + COEP). COEP applies recursively to iframes, which conflicts with third-party ad iframes; the credentialless escape hatch is not Baseline; and AdSense documents no COEP support. Measured messaging and transfer costs are already negligible (traces are transferred zero-copy).

### 2.2 Monte Carlo wall time vs worker count (Chromium, real app, `navigator.hardwareConcurrency` overridden)

| Scenario                                | 1 worker | 2             | 3             | 4             | 8      |
| --------------------------------------- | -------- | ------------- | ------------- | ------------- | ------ |

- Scaling is near-linear 1→2 and flat after 3 in this VM. The browser's own processes (renderer, compositor, software GPU) compete with the workers.
- With 4 workers, 2 of 4 runs produced **unattributed** main-thread long tasks of 56–155 ms during the run. LoAF entries had `blockingDuration` up to 111 ms and no script attribution, which points to CPU starvation rather than JS.
- Chunk size (Node, 40 heavy runs): 1 run/chunk vs 3 (the current `CHUNKS_PER_WORKER = 4`) is identical (4.21 vs 4.17 s with 4 threads), and 10 is about 13% slower. **The current chunking is fine.**

No long tasks came from progress messages (they are throttled to 100 ms).

`aggregate()` alone in Node: 9.8 ms (500 runs), 90 ms (5,000), 435–447 ms (20,000). `buildDesign` on the main thread adds 7–30 ms. Structured clone of `RunSummary[]` objects is 28 ms for 20,000 runs (3.5 MB JSON-equivalent), versus 1.9 ms for the same data packed in a `Float64Array`.

Prototype (`aggopt.ts`, identical results to 1e-12): ranking `trexAdvantage` once (instead of 22 times inside `spearman`) and sorting a `Uint32Array` of indices keyed by a `Float64Array` makes the sensitivity part **1.5x / 2.6x / 2.0x** faster at 500 / 5,000 / 20,000 runs (373 → 184 ms at 20,000).

## 3. Techniques: what applies here and what doesn't (with sources)

| Technique                                                      | What the source says                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                          | Fit for this project                                                                                                                                                                                                                                                                                                                                                                                              |
| -------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- | ----------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------------- |
| **SoA / typed arrays**                                         | V8 tracks "elements kinds"; packed, specific kinds are optimised more aggressively and transitions only go toward more generic kinds ([v8.dev/blog/elements-kinds](https://v8.dev/blog/elements-kinds)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | The engine already uses SoA `Float64Array`/`Int32Array`. The remaining wins are **algorithmic** (§2.1). `RunSummary[]` objects could become a packed `Float64Array` (9 fields) for transfer and aggregation (measured 28 → 1.9 ms clone at 20k runs).                                                                                                                                                             |
| **Avoid closures and megamorphic calls in hot loops**          | Inline caches go polymorphic and then megamorphic beyond a small degree (e.g. 4 for property loads in V8); megamorphic sites fall back to a global table ([mrale.ph](https://mrale.ph/blog/2015/01/11/whats-up-with-monomorphism.html)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                      | `grid.query` and `grid.nearest` take callbacks from 2 closures each (polymorphic, not megamorphic). The measurable cost is the **redundant filter** (`trexAliveFilter`, 8.5% self time) rather than closure dispatch. Specialise `nearest` for "no filter" and keep 1–2 call targets per site. Profile-guided; the dispatch-overhead claim is not measured separately (**unverified**).                           |
| **postMessage / structured clone**                             | Clone cost scales with object complexity; JSON size predicts it; up to ~100 KiB is fine for interactions and ~10 KiB during animations; `ArrayBuffer` transfer is size-independent ([surma.dev](https://surma.dev/things/is-postmessage-slow/)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Progress messages are tiny. Result messages are ~180 B/run, so a 5,000-run chunk is about 0.9 MB of objects, still fine off-animation. Traces are already transferred. Low priority; pack summaries if aggregation moves into a worker.                                                                                                                                                                           |
| **Chunk sizing**                                               | — (own measurement)                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                           | 1 vs 3 runs/chunk: identical; 10: 13% slower (§2.2). Keep `CHUNKS_PER_WORKER = 4`. Optionally cap chunk duration with the (recalibrated) cost model.                                                                                                                                                                                                                                                              |
| **Pool size**                                                  | `hardwareConcurrency` = logical processors available ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Navigator/hardwareConcurrency)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                 | Measured: 4 workers ≈ 3 workers in the browser, but 4 workers caused 56–155 ms unattributed main-thread stalls. Use `hc − 1` (min 1, max 8).                                                                                                                                                                                                                                                                      |
| **Yielding / long tasks**                                      | Tasks > 50 ms are long; `scheduler.yield()` continues in a prioritised task (Chrome/Edge 129, Firefox 142, not Safari) ([web.dev optimize-long-tasks](https://web.dev/articles/optimize-long-tasks)). LoAF (Chrome 123+) attributes long frames to scripts ([developer.chrome.com](https://developer.chrome.com/docs/web-platform/long-animation-frames)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                    | Use for result rendering (cards → charts → tornado), the language switch and startup. Use LoAF in a perf test and later in RUM.                                                                                                                                                                                                                                                                                   |
| **OffscreenCanvas in a worker**                                | Baseline widely available; `transferControlToOffscreen()` moves canvas rendering into a worker ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/OffscreenCanvas), [web.dev](https://web.dev/articles/offscreen-canvas)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | JS draw is only 1.5–6 ms/frame, so the gain is **isolation**: the replay keeps animating while the main thread aggregates, switches language or runs ad scripts. Medium–high effort (theme colours, DPR, resize, events). Do this after LOD.                                                                                                                                                                      |
| **Path2D batching**                                            | Path2D objects can be cached and reused ([MDN Path2D](https://developer.mozilla.org/en-US/docs/Web/API/Path2D)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | Tigers are already batched per state. T-Rex are drawn one by one with a fresh `rgb()` string each. Batch by quantised HP colour (e.g. 16 buckets) into Path2D, which turns ≤ 1,000 draw calls into ≤ 32 (not measured separately).                                                                                                                                                                                |
| **Integer coords, alpha:false, layered canvases, CSS scaling** | MDN canvas optimisation: avoid sub-pixel coordinates, pre-render repeated primitives, layer static and dynamic content in multiple canvases, use `{alpha:false}` when the backdrop is opaque ([MDN Optimizing canvas](https://developer.mozilla.org/en-US/docs/Web/API/Canvas_API/Tutorial/Optimizing_canvas)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                               | The replay background is opaque, so use `alpha:false`. Put the arena, scale bar and dead-tiger marks on a static layer in fixed zoom. Snap tiny dots to device pixels.                                                                                                                                                                                                                                            |
| **rAF budgeting**                                              | rAF follows the display refresh (60/120/144 Hz) and pauses in background tabs ([MDN](https://developer.mozilla.org/en-US/docs/Web/API/Window/requestAnimationFrame)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                         | The replay already pauses when hidden or off-screen (IntersectionObserver). Add an **adaptive quality controller**: if the median frame interval exceeds 20 ms, step down (LOD → DPR 2 → DPR 1.5). On 120 Hz screens, consider drawing every other frame for > 2,000 agents.                                                                                                                                      |
| **content-visibility**                                         | `content-visibility: auto` skips rendering of off-screen content; their demo went from 232 → 30 ms initial render ([web.dev](https://web.dev/articles/content-visibility)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                   | Apply to the results panel (hidden until a run), long content sections on the coming guide and tutorial pages, and the closed advanced table. Pair with `contain-intrinsic-size` to avoid CLS.                                                                                                                                                                                                                    |
| **Font loading**                                               | `swap` = 0 ms block / infinite swap; `optional` = 100 ms block / no swap; preload ignores `unicode-range`; swaps can shift layout ([web.dev font best practices](https://web.dev/articles/font-best-practices)).                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                                              | 92 `unicode-range` faces → 14 swaps → 6–8 long tasks. Prefer a **build-time subset** of the glyphs actually used by UI and content (1–2 files, one preloaded), or load faces in one batch via the CSS Font Loading API. `optional` would conflict with the owner's "always Pretendard" requirement on first visits.                                                                                               |
| **SharedArrayBuffer**                                          | Needs a secure context and cross-origin isolation ([MDN SAB](https://developer.mozilla.org/en-US/docs/Web/JavaScript/Reference/Global_Objects/SharedArrayBuffer)). **Cross-track notes (affect perf decisions):**

- **AdSense CSP.** AdSense says CSP is optional, but if used it supports **only strict CSP**: `script-src 'nonce-{random}' 'unsafe-inline' 'unsafe-eval' 'strict-dynamic' https: http:`, `object-src 'none'`, `base-uri 'none'`. Domain allowlists are explicitly unsupported ([AdSense Help 16283098](https://support.google.com/adsense/answer/16283098?hl=en)). A per-response nonce cannot come from a static `_headers` file. It needs a Pages Function or Worker (HTMLRewriter) on HTML responses, which adds a little TTFB and uses Workers quota (size of that cost **not measured**).
- **Version reset feature (owner request).** `Clear-Site-Data: "cache"` and `"storage"` are origin-scoped, but **`"cookies"` clears cookies for the whole registered domain including subdomains**, i.e. all of `vinylims.com`, which would include AdSense's first-party cookies ([MDN Clear-Site-Data](https://developer.mozilla.org/en-US/docs/Web/HTTP/Reference/Headers/Clear-Site-Data); Baseline since 2023-09, HTTPS only).
  - A static `_headers` rule on a dedicated path (e.g. `/reset`) can send `"cache", "storage"` without JS.
  - HTML is already `no-cache` and assets are hashed and immutable, so a normal reload already picks up a new release. The version check only needs a tiny `version.json` fetched with `cache: 'no-store'`.
- **Speed Brain.** Production sends Cloudflare's `Speculation-Rules` header, which conservatively prefetches likely next navigations ([Cloudflare docs](https://developers.cloudflare.com/speed/optimization/content/speed-brain/)). That will help once guide and tutorial pages exist.

## 5. Caveats and unverified items

- All browser numbers come from one 4-vCPU VM with a **software GPU** (SwiftShader). Raster-bound results (replay, canvas methods) will be faster on real GPUs, but the method ranking (arcs ≫ rects) is the usual one for software raster and is **unverified on mobile GPUs**.
- Hangul layout cost in this container uses fallback system fonts (WenQuanYi), so absolute startup times are environment-specific (§2.5).
- No field data: PageSpeed Insights quota was exhausted and CrUX was not checked. INP figures are lab proxies from Event Timing entries.
- Several claims are marked **unverified**:
  - that AdSense does not support COEP (no statement found either way);
  - the TTFB cost of a nonce-injecting Pages Function;
  - the WASM/SIMD gain for this engine;
  - the expected gains from #6 and #7.
- The #8 model change was compared on small samples (3–400 runs per config); a proper statistical comparison is needed before adopting it.
